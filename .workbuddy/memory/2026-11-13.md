## Electron 启动失败 ERR_EMPTY_RESPONSE 的根因与修复

- 现象：`npm run dev` 弹窗 `SuperTing Startup Error: ERR_EMPTY_RESPONSE (-324) loading 'http://localhost:5183/'`，同时日志有 `CLI bridge failed to start: No available ports in range 8200-8219`。
- 致命根因不是端口/Vite 竞态，而是**系统代理**：用户用 iPhone 热点 + Shadowrocket，电脑手动设系统代理 `172.20.10.1:1082`，且 `ProxyOverride` 被设成 `<-loopback>`（含义是"连 localhost 也走代理"）。Chromium/Electron 加载 `localhost:5183` 时请求被发到手机代理，拿不到 Vite 页面 → ERR_EMPTY_RESPONSE。
- 实测对照：直连 `curl --noproxy '*' http://localhost:5183/` → HTTP 200；`curl --proxy http://172.20.10.1:1082` 请求同一地址 → 超时 0 字节。
- 修复（已执行）：注册表 `HKCU:\Software\Microsoft\Windows\CurrentVersion\Internet Settings` 的 `ProxyOverride` 从 `<-loopback>` 改为 `localhost;127.0.0.1;[::1];<local>`；`ProxyEnable` 保持 1、`ProxyServer` 保持 `172.20.10.1:1082`（不影响翻外网）。原值如需还原即 `<-loopback>`。
- 已在"代理开启"状态下端到端验证：`NODE_ENV=development node scripts/run-electron.js --dev` 正常启动，窗口标题 `Voice Recorder`，Qdrant 等初始化完成，不再报 ERR_EMPTY_RESPONSE。
- 非致命的第二个根因：`netsh interface ipv4 show excludedportrange protocol=tcp` 显示 **8139–8238 是 Windows 保留端口段**（Hyper-V/WSL 的 winnat 动态保留），8200–8219 全在里面，实测 bind 返回 `EACCES`、9200 正常。`cliBridge.start()` 的失败被 `.catch()` 吞掉只打日志，App 仍能启动；但 CLI / MCP 桥接、以及同样用 8200 段的 llamaServer/whisperServer 会不可用。可选解法：重启电脑让保留段重新分配，或以管理员执行 `net stop winnat && net start winnat`；改源码端口段需同步改 CLI 端，不建议。
- 注意：手动验证时若漏了 `NODE_ENV=development`，会走生产分支报 `HTML file not found: src/dist/index.html`，与真问题无关。正确 dev 启动脚本是 `npm run dev`（`concurrently -k -r dev:renderer + dev:main`）。
- 启动后仍存在的非致命告警：Qdrant `Client version 1.17.0 is incompatible with server version 1.20.0`（下载的 qdrant 二进制版本偏新，向量检索可能受影响）；`nircmd.exe` / `windows-mic-listener.exe` 缺失走 fallback；whisper-server、sherpa-onnx、模型文件均缺失（本地转录不可用）。

## 关闭 Silero VAD 后即可录音：根因确认（实测）

- 用户实测关闭「听写使用 Silero VAD」后录音正常，确认瓶颈在 VAD 而非麦克风、FFmpeg、模型或本地静音门控。
- 当前应用实际启动参数（PID 30776）：`--port 13219 --language auto --vad --vad-model ...ggml-silero-v5.1.2.bin --vad-threshold 0.3 --vad-min-speech-duration-ms 250 --vad-min-silence-duration-ms 200 --vad-max-speech-duration-s 30 --vad-speech-pad-ms 100 --vad-samples-overlap 0.5`。说明用户已按前一条建议把阈值降到 0.3，**但问题依旧**。
- 决定性对照实验（同一 base 模型、同一批 JFK 16k 单声道样本，VAD on / VAD off 两个 server）：11s 正常音量、15% 音量、5% 音量、0.9s、前导静音样本两边都能出文本 → 阈值/音量不是主因。0.2s / 0.3s 极短样本：VAD on 返回 `{"text":""}`（空文本），VAD off 分别返回 `[BLANK_AUDIO]` / `And...`。
- VAD server stderr 给出铁证：0.2s、0.3s 样本日志为 `processing 'audio.wav' (3200/4800 samples ...)` + `whisper_vad_segments_from_probs: Final speech segments after filtering: 0`（没有后续的 `detected N speech segments` 和 `Reduced audio`）；0.5s 样本为 `1` 段。即 VAD 判 0 段时 whisper.cpp 直接跳过推理返回空文本。
- 主因是 `--vad-min-speech-duration-ms 250` 的时长门限（叠加 VAD 512 样本窗口对极短音频判定不稳），**不是概率阈值**。更正前文「把阈值降到 0.3」的建议：降阈值无效，应降 `whisperVadMinSpeechDurationMs`。
- 验证宽松组合（threshold 0.1 + minSpeech 50 + minSilence 50 + overlap 0.1）：0.3s 样本恢复 `And...`，与无 VAD 结果一致，证明参数可调且不必须关闭 VAD。
- 完整因果链：短听写 → VAD 过滤后 0 段 → whisper.cpp 跳过推理返回空文本 → `whisper.js parseWhisperResult` 把空文本/`[BLANK_AUDIO]` 统一译为 `No audio detected` → `no-audio-detected` → UI「未检测到音频」且录音不落盘。关闭 VAD 后整段音频（含前后静音）被 pad 到 30s 窗口，短句也能识别，所以立刻可用。
- 次要发现：`whisper-server --help` 中 `--vad-samples-overlap` 含义是「seconds between segments」（默认 0.10），但项目常量/UI 当作 0~0.95 比例、默认传 0.5，属语义误用；非本次主因。
- 可选根治（未做）：VAD 判空时自动以无 VAD 重转一次兜底，避免误杀并保留录音；或把听写场景 VAD 默认值改为关闭/更宽松。
- 本轮仅做诊断与临时对照实验，未改动项目源码；验证用的 9200/9201/9202 三个 whisper-server 与临时音频/脚本均已清理。

## 设置弹窗关闭 X 在窗口化状态下点不中（已修复）

- 现象：窗口化（restored）时 `SettingsModal` 右上角 X 点不动，最大化后可以点。
- **根因判定：Electron frameless 窗口的 `-webkit-app-region: drag` 矩形由 Windows `WM_NCHITTEST` 在系统层命中，先于 DOM z-index；落在其中的 pointerdown 被当作 HTCAPTION 拖动窗口，click 不派发。最大化时 Windows 不允许拖动窗口，于是点击正常 —— 这正是「窗口化不行/全屏可以」的判据，与坐标、z-index、动画无关。** 上一轮为补窗口按钮新增的 `<main>` 顶部 `h-10 w-full` 全宽 drag 条（以及侧边栏两块 drag、`index.css` 的 `.ow-page-header` drag）放大了该冲突；项目此前所有 Radix dialog 都没有 any app-region 处理。

## 悬浮窗点击无法停止录音（删除 ESC 后暴露，已修复）

- 现象：录音中点击悬浮窗（蓝球 toggleListening）无效，日志只有一对 `Window drag started/stopped`（dragManager.js:36/49）。此前一直用 ESC 全局取消，点击路径从未真正用过，删 ESC 后暴露。

- 修复（惰性拖动，2 个文件）：
  1. `src/hooks/useWindowDrag.js`：`handleMouseDown` 只"武装"（isDragging=true + dragStartedRef=false），不再调 startWindowDrag；新增 `activateDrag()`，由消费方在位移超阈值时调用并真正 `startWindowDrag`；`handleMouseUp` 仅在 `dragStartedRef` 为真时 `stopWindowDrag`（原地点击不再产生 drag started/stopped 日志）。删除无消费者的 `handleClick`。
  2. `src/App.jsx`：onMouseMove 超过 5px 时 `setHasDragged(true)` 后调用 `activateDrag()`；其余事件流不变（`hasDragged` 仍决定 click 是否 toggle、右键菜单是否打开）。
- 行为：原地点击 → click 正常 → `toggleListening()` 停止并转写；按住移动 >5px → 才真正拖动窗口，click 被 `hasDragged` 抑制。`isDragging` 仍驱动 grabbing 光标（armed 期间同旧行为）。Vite 转译 App.jsx 200/57601B、useWindowDrag.js 200/6089B 验证通过。

### 修复：运行时镜像「没生效」的真因（isRetryable 不认 Electron 错误码）

- 用户日志：`ggml-small.bin` 下载 `net::ERR_CONNECTION_TIMED_OUT`，**只有一条 Download failed、没有任何 Retrying**，说明重试循环一次都没跑，镜像自然没轮到。
- 根因：`src/helpers/downloadUtils.js` 的 `downloadAttempt` 用 Electron `net.request`，其连接失败是 `net::ERR_CONNECTION_TIMED_OUT`（`error.code` 常常为空，只有 `message`）；而 `isRetryable()` 只检查 Node 风格的 `RETRYABLE_CODES`（ECONNRESET/ETIMEDOUT…），于是判定为不可重试 → 直接 `Download failed` 并 throw。
- 修复：新增 `RETRYABLE_NET_ERRORS`（Chromium/Electron 错误名列表：ERR_CONNECTION_TIMED_OUT / ERR_TIMED_OUT / ERR_CONNECTION_RESET / ERR_CONNECTION_CLOSED / ERR_CONNECTION_ABORTED / ERR_CONNECTION_FAILED / ERR_NAME_NOT_RESOLVED / ERR_ADDRESS_UNREACHABLE / ERR_EMPTY_RESPONSE / ERR_NETWORK_CHANGED / ERR_SOCKET_NOT_CONNECTED / ERR_SSL_PROTOCOL_ERROR），`isRetryable` 在 code 不命中时用 `code + message` 文本匹配。
- 验证（真实 Electron 主进程跑 `downloadFile`，临时脚本已删）：CANDIDATES=`[huggingface.co, hf-mirror.com]`；首次直连失败后日志出现 `Retrying download { url: 'https://hf-mirror.com/...' }`，`E2E_OK bytes=885098`，34s 完成。
- 生效条件：主进程改动需**重启应用**（HMR 不覆盖主进程）。用户 `.env` 当前 `injected env (0)`（无任何变量），即未设 off，镜像兜底按默认启用。
- 顺带发现（未处理）：日志中 Parakeet 报 `model "base" not downloaded` —— 本地引擎为 NVIDIA/Parakeet 时却传入了 whisper 的模型名 `base`，属设置/参数串联问题，待用户确认后再修。
